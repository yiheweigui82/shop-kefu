## 这是什么

一个**桌面端 AI 客服系统**（PyQt6），为电商卖家做的：AI 自动回复客户咨询、能查商品知识、能回答售后政策、答不了就转人工。

> **已支持平台**：拼多多 ✅　·　淘宝 / 天猫（千牛）✅　·　**抖音（飞鸽）✅ 已跑通，准备上线**　·　京东（京麦）/ 1688 🚧 规划中

📖 **详细功能说明**：[`docs/功能说明.md`](docs/功能说明.md) —— 双渠道能力对比 · **媒体发送专章（图片/视频）** · 消息治理 · 行为护栏 · 已知限制 · 代码地图
📗 **单通道详解**：[`docs/淘宝千牛通道-功能说明.md`](docs/淘宝千牛通道-功能说明.md) —— 千牛通道架构 · WS 协议栈 · 消息治理 · **转人工（售前/售后分派 + 失败自动回退）**

**核心设计：一平台一个通道（Channel），通道对称、内核共用。**

```
                    ┌─────────────────────────────┐
   拼多多  ──┐       │                             │
   淘宝/天猫 ─┤       │      AI 客服内核（共用）      │
   抖音/飞鸽 ─┼──────▶│  Agent 框架 / 双知识库 /     │
   京东    ──┤       │  消息队列 / 工具链 / UI       │
   1688    ──┘       │                             │
                    └─────────────────────────────┘
```

**通道只负责「接进来、发出去」**；消息队列、AI 内核、知识库、工具链**完全复用**。
一个实例 = 一个店 = 一个独立线程 + 独立事件循环，**多店可共存在同一进程内**。

## 功能特性

### 通用能力（所有通道共用）

- **AI 智能回复** —— 自研 Agent 框架（不依赖第三方 Agent 库），多轮工具调用 + 会话上下文管理
- **双知识库** —— **商品知识库**（规格、成分、用法）+ **客服知识库**（售后/物流/退款政策），分别检索
- **商品知识自动同步** —— 从平台拉取商品列表 → 多模态 LLM 提取知识入库（**图片也参与理解**）
- **图片 / 视频识别** —— 客户发的图片、视频走视觉预处理，识别结果注入对话上下文
- **多形态发送** —— AI **不止发文字**：可发送**图片、视频、商品卡片**，也可按需发送链接等富文本
- **转人工** —— 按平台机制转接（关键词触发 / AI 判定 / 兜底）
- **消息合并** —— 客户连发多条合成一段给 AI 理解，避免刷屏式逐条回复
- **多 LLM 供应商** —— DeepSeek / 火山引擎 / Kimi / 智谱 / Qwen / 任意 OpenAI 兼容端点

### AI 可用工具

| 工具 | 作用 |
|---|---|
| `get_shop_products` | 查店铺商品列表（价格区间、销量、库存） |
| `send_goods_link` | 给客户发商品卡片 |
| **`send_media`** | **发图片 / 发视频**（`media_type=image\|video`）—— 渠道适配层吸收平台协议差异，AI 侧零改动 |
| `get_product_knowledge` | 查某商品的详细知识 |
| `search_customer_service_knowledge` | 搜客服知识库（售后/物流/退款政策） |
| `transfer_conversation` | 转接人工客服 |

## 淘宝 / 千牛通道

**协议层**：换 accessToken（含令牌过期自动刷新）→ 注册 → 状态同步 → 建同步流 → 定时心跳 → 逐帧 ack。

| 能力 | 说明 |
|---|---|
| 千牛 WS 协议栈 | 逆向实现的私有长连接协议 |
| 历史消息拉取 | 从推送包解密发现会话 → 调接口，结果**从推送回来**，按时间窗收集 |
| 请求签名 | 本地 JS 引擎执行签名脚本 |
| **令牌轮换** | 平台约 1.5 小时轮换签名令牌 → **收到响应 `Set-Cookie` 即刻更新**，且**主令牌与加密令牌必须成对更新**（只更新一个会「非法令牌」）|
| 断线自愈 | 指数退避重连 + **读超时强制重连**（长连接僵死兜底）|

**消息接入与治理**（都是生产环境踩出来的）：

| # | 问题 | 解法 |
|---|---|---|
| 1 | 会话 id 有多种写法（带/不带后缀、主账号/子账号），按原串判重全漏 | 会话 id **归一化**（只保留买家段），判重/在途/失败计数统一用归一化键 |
| 2 | 进程重启后已处理消息被当新消息**重放** → 同一客户被连回多次 | 已处理消息指纹落盘，**投递时立即落盘**（不等批量攒够）|
| 3 | 个别会话永远拉不到 → 每轮白等 | 按归一化键累计失败，达阈值 → 「僵尸会话」跳过；**收到该会话推送自动救回** |
| 4 | 白天接待过的会话长期滞留 → 空转烧接口 | **空转降频**（连续 N 次无新增则降频，来新消息立刻恢复），实测接口调用**省约 87%** |
| 5 | 拉历史串行 → 一个慢会话堵住全部 | **并发拉取 + 并发上限**，按归一化键**防重入** |
| 6 | 客户连发多条 → AI 逐条回复刷屏 | **消息合并器**：窗口内合并；含媒体时整窗只发一条安抚 |
| 7 | 平台本地接待列表可能长时间不更新 → 漏收 | 接待列表**双源**：本地文件 + 远程接口 |

**业务能力**：

| 能力 | 说明 |
|---|---|
| **场景卡主动接话** | 客户从商品详情页/订单页进来时**主动问好**（不是沉默等待），**按卡片类型分别冷却** |
| **会话转回后问好** | 平台把会话转回来 → 主动问好，冷却键**独立**（否则「转出去问过 → 转回来不发」）|
| **回复后补商品卡** | AI 回复后补 1 张相关商品卡，同一商品**只发一次**（平台会拦截连续发卡）|
| **人工让位** | 人工刚说过话（滑动时间窗）或已转人工 → **AI 不插话** |
| **漏回治理** | 客户最后发言超阈值（默认 30 分钟）而我方一直没回 → 主动安抚/追问；**每会话只发一次**、每轮限 N 条 |

**转人工**：走平台 mtop 接口，目标是**客服分流组**（不是客服 uid 列表）。每个店的组不同，通道会在验证账号时**自动采集该店全部客服组**并落盘（手工配置只作兜底）。

**按诉求分派 + 失败自动回退**（千牛通道特有）：采集到的组按**组名**（「售前」/「售后」）分类，转人工时按客户诉求排候选顺序 —— **售前诉求先试售前组、售后诉求先试售后组**，末尾兜底到该店其它组 / 默认组；某组**当前无人值班**（平台回「该分组找不到可以转交的客服」）→ **自动换下一组**，不再一条路走到黑。诉求判据是**确定性代码**（会话出现过订单信号 → 售后；话头命中退/换/修/破损/漏发… → 售后；都不中 → 售前），不依赖模型判断，逐条可单测、判错也有回退兜底。

**已知限制**：

1. **无「设置客服在线」的开放接口** —— 在线态由客户端维持，通道侧的「上线」= 接管并连上 WS
2. **平台私有协议** —— 协议为逆向实现，平台改动可能导致通道短时失效
3. **媒体链接带时效签名** —— 会过期，不能存死；跨渠道共享时不带媒体
4. **登录态过期只能人工重新登录** —— 令牌刷新可自动完成，但会话过期无法程序化恢复
5. **同账号双端互踢** —— 平台机制，同一客服账号多处登录会互相踢

## 新店接入的自动化

**加一个账号 = 一次登录，其余自动完成。**

点「验证」拿到登录态之后，系统**自动**做三件事：

**① 抓店铺 logo**
回店铺后台首页，轮询页面图片，按**图库路径**判断哪个是店标，写库。
> 铁律：**只认可靠图库**（`shopmanager` 头像 / `tfs` 店铺图库），**识别不出就留空** —— **宁可没有，也绝不乱显示**。

**② 查转人工客服组**
打开「客服分流」页，读页面自身发出的接口响应，拿到该店**全部分组**，按规则选：
> 组按**组名**分类出**售前组 / 售后组**，转人工时**按客户诉求排候选顺序并逐个试**（某组无人值班就自动换下一组）。
> 结果落盘，转人工时自动取用。**以后加新店，验证一次就配好了。**

**③ 同步商品**
「知识库」页点同步即可拉取该店商品（列表 → 逐个提知识入库）。
> **淘宝店和天猫店的入口不同**，实现里**不写死 URL、不写死接口名** —— 先落首页找菜单，再收任何含商品数据的响应，所以两类店都能用。

## 快速开始

**环境**：Python ≥ 3.11，Windows（打包为 exe 后可独立运行）

```bash
# 安装依赖
uv sync

# 启动
python app.py
```

首次运行会生成 `config.json`，在「系统设置 → LLM 模型配置」里填 API Key（**支持 DeepSeek / 火山 / Kimi / 智谱 / Qwen / 任意 OpenAI 兼容端点**）。
API Key 使用 **Windows DPAPI** 加密后落盘。

**添加账号**：填平台账号（+ 可选密码，用于掉线后自动重登）→ 点「验证」→ 弹出浏览器完成登录 → 其余自动。

**构建 Windows 安装包**：

```bash
python scripts/build_win_exe.py --clean
```

推送 `v*` 标签会触发 CI 自动构建并发布 Release。

## 项目结构

```
├── Agent/                  # AI 代理模块（自研 Agent 框架）
│   └── CustomerAgent/
│       ├── custom/         # LLM 客户端、会话管理、工具执行器
│       └── tools/          # Agent 工具集
├── Channel/                # 渠道集成（一个平台一个目录，结构对称）
│   ├── pinduoduo/          # 拼多多通道
│   │   ├── core/           # 连接、生命周期、状态、消息处理
│   │   └── utils/API/      # 平台接口封装
│   └── taobao/             # 淘宝 / 千牛通道
│       ├── core/           # 协议栈、连接、生命周期、状态、转人工、签名
│       └── handlers/       # 业务 handler、消息合并器
├── Message/                # 消息处理（队列 + 处理器链）
├── bridge/                 # 桥接（Context / Reply / SendService）
├── core/                   # 核心服务（DI 容器、连接状态）
├── database/               # SQLAlchemy + 知识服务 + 商品同步
├── service/                # 服务层
├── ui/                     # PyQt6 界面
├── utils/                  # 日志、路径等
├── scripts/                # 构建与抓包脚本
└── app.py                  # 应用入口
```

**技术栈**：PyQt6 + pyqt6-fluent-widgets · LiteLLM（直接异步调用，无需 Proxy）· SQLAlchemy + SQLite · jieba（知识检索）· asyncio + websockets · Pydantic · Loguru

## 开发规范

**新增/修改平台接口前**：

1. **先用 curl 或 Python 脚本实测接口**，确认真实参数、请求头、响应结构
2. **按实际响应结构写解析**，不要凭猜测写字段名
3. **改完用真实调用或 mock 验证**解析逻辑

> 例：某平台商品列表，数据在 `result.onSaleGoods` 而非 `result.goodsList`，字段是驼峰 `goodsId` 而非下划线 `goods_id`，价格单位是「分」要除以 100。**猜字段名 = 必然返工。**
