# 淘宝 / 千牛（Qianniu）客服通道 · 功能说明

> 本文档描述一个**电商客服 agent 内核**里「淘宝 / 千牛」渠道通道（Channel 插件）已实现的能力。
> 通道与同项目内的拼多多通道**结构对称**：一个实例 = 一个店 = 一个独立线程 + 独立事件循环，
> 多个店可共存在同一进程内。
>
> 文档为**通用说明**：不含任何具体店铺、账号或部署环境信息。

---

## 1. 架构定位

```
Channel/taobao/
├── taobao_channel.py            通道类（Mixin 组合 + 统计）
├── taobao_message.py            消息模型（含会话 id 扩展）+ 帧归一化
├── taobao_sender.py             发送器（文本/图片/视频/商品卡/转人工）
├── core/
│   ├── taobao_config.py         账号参数（含转人工参数）
│   ├── taobao_source.py         千牛 WS 消息源（协议栈主体）
│   ├── taobao_connection.py     连接 + 指数退避重连
│   ├── taobao_message_handler.py 帧 → 上下文 → 队列；handler 链装配
│   ├── taobao_lifecycle.py      启动/停止/消息循环/心跳
│   ├── taobao_state.py          每店会话状态（冷却/已发卡/让位/入口商品）
│   ├── mtop_transfer.py         转人工（mtop cloudkefu.forward）
│   ├── taobao_sign.py + js/     请求签名（本地 JS 引擎执行）
│   └── taobao_message_*.py
└── handlers/
    ├── business.py              业务 handler（场景卡/转回问好/补商品卡/合并）
    └── merger.py                客户连发消息合并器
```

**与其它渠道共用**：消息队列 / 消费链 / AI 内核 / 知识库 / 工具链完全复用——通道只负责"接进来、发出去"。

## 2. 连接与协议

| 能力 | 说明 |
|---|---|
| 千牛 WS 协议栈 | 换 accessToken（含令牌过期自动刷新重试）→ 注册 → 同步状态同步 → 建立同步流 → 定时心跳 → 逐帧 ack |
| 历史消息拉取 | 从推送包解密发现会话 id → 调历史消息接口，结果**从推送回来**，按时间窗收集 |
| 消息发送 | 按接收方作用域发送；会话 id 带平台域后缀 |
| 请求签名 | 本地 JS 引擎执行签名脚本（依赖 Node），签名参数含令牌与时间戳 |
| 令牌轮换 | 平台定时轮换签名令牌（约 1.5 小时）→ **收到响应 `Set-Cookie` 即刻更新**，并**成对更新**主令牌与其加密令牌（只更新一个会导致「非法令牌」） |
| 断线自愈 | 指数退避重连（有限次）+ **读超时强制重连**（长连接僵死兜底） |
| 心跳 | 定时心跳保活，心跳异常计入失败计数并触发退避 |

## 3. 消息接入与治理

生产环境实测暴露的问题与对应实现（这些是稳定性核心）：

| # | 问题 | 实现 |
|---|---|---|
| 1 | 会话 id 有多种写法（带/不带后缀、主账号/子账号），按原串判重全漏 | 会话 id **归一化**（只保留买家段），判重 / 在途 / 失败计数统一使用归一化键 |
| 2 | 进程重启后，已处理的客户消息被当成新消息**重放** → 同一客户被连回多次 | 已处理消息指纹落盘；**投递新消息时立即落盘**（不等批量攒够），重启后按最新指纹判重 |
| 3 | 个别会话永远拉不到（超时/无权限）→ 每轮白等，拖慢整轮轮询 | 失败按**归一化键**累计，达阈值 → 加入"僵尸会话"列表跳过；**收到该会话推送自动救回** |
| 4 | 白天接待过的会话长期留在轮询列表，客户早不说话 → 空转烧接口 | **空转降频**：连续 N 次"无新增"→ 该会话降频拉取；**来新消息立刻恢复**高频（实测接口调用省约 87%） |
| 5 | 拉历史串行 → 一个慢会话堵住后面所有 | 改**并发**拉取，并加**并发上限**（超限当轮跳过、下轮再来）+ 按归一化键**防重入** |
| 6 | 客户连发多条消息，AI 逐条回复 → 刷屏 | **消息合并器**：窗口内多条合成一段供 AI 理解；含媒体时整窗只发一条安抚；窗口到点兜底触发 |
| 7 | 平台本地接待列表文件可能长时间不更新 → 期间客户消息漏收 | 接待列表**双源**：本地列表文件 + 远程接待列表接口 |

## 4. 自动回复业务能力

| 能力 | 说明 |
|---|---|
| AI 自动回复 | 与其它渠道共用同一套 AI 内核（多轮工具调用 + 知识库检索） |
| 图片 / 视频识别 | 客户发的图片、视频走视觉预处理，识别结果注入对话上下文 |
| **场景卡主动接话** | 客户从商品详情页 / 订单页入口进来时**主动问好**（不是沉默等待）；**按卡片类型分别冷却**（订单卡不该挡住商品卡） |
| **会话转回后问好** | 平台把会话转回来（系统消息）→ 主动问好；冷却键**独立**（否则"转出去时问过 → 转回来不发了"） |
| **回复后补商品卡** | AI 回复后补发一张相关商品卡；**只发 1 张**、同一商品**只发一次**（平台会拦截连续发卡） |
| **人工让位** | 人工客服刚说过话（滑动时间窗），或该会话已转人工 → **AI 不插话** |
| 兜底 | AI 生成/发送失败 → 走兜底流程（先尝试转人工，再如实告知） |
| 发送能力 | 文本 / 图片 / 视频 / 商品卡 |

## 5. 转人工

- 走平台 mtop 接口 `cloudkefu.forward`（h5 网关签名），目标是**客服分流组**（不是客服 uid 列表）。
- **客服组自动采集**：登录 / 校验账号时自动探测该店**全部**客服分流组（编号 + 组名）并落盘；
  配置文件里的手工映射只作**兜底**，环境变量用于单店注入 → 接新店不必再手工挖隐藏 ID。
- **按诉求分派 + 失败自动回退**（本通道特有）：
  - 采集到的组按**组名**（「售前」/「售后」）分类，转人工时按客户诉求生成**候选顺序**；
  - **售前诉求 → 先试售前组，不成再试售后组**；**售后诉求 → 先试售后组，不成再试售前组**；
    顺序末尾再兜底到"该店其它组"→"配置的默认组"；
  - 平台返回「该分组找不到可以转交的客服」（= 该组当前无人值班）→ **自动换下一组**，不再"一条路走到黑"；
  - **中止回退**只有两种：① 平台说"转交对象就是当前接待账号"（转给自己，换组无意义）；
    ② 该店根本没有配置任何组；
  - 该店只有一个组时 → 按该组转（无可回退对象）。
- **诉求判据 = 确定性代码**（不依赖模型判断，避免 LLM 判错）：
  1. 会话里出现过**订单信号** → 售后（已下单）。订单号三处来源：消息扩展字段里的 `orderId`、
     形如 `<场景名>#<订单号>_<时间戳>` 的会话唯一 ID、场景卡文案「当前用户来自 订单…」；
  2. 否则客户话里明确是**售后问题**（退 / 换 / 修 / 保 / 破损 / 漏发 / 发错 / 质量…）→ 售后；
  3. 都没有 → 售前（购买前咨询）。
  - 判据逐条可单测；判错也有回退兜底（先试错的那组，转不成自动换组）。
- 令牌过期自动换新后重试（主令牌 + 加密令牌成对更新）。
- 兜底：主链路不可用时，独立脚本可**直连 mtop** 发起转接（不依赖常驻进程）。
- 常见返回：分组里找不到客服（组无人值班 / 组配错）/ 转交失败（未配置组）/ 令牌过期（可自动刷新）/
  会话过期（**需重新登录**）。

## 6. 漏回治理：主动触达

- 客户最后一次发言超过阈值（默认 30 分钟）而**我方（AI 或人工）一直没回** → 主动发一条安抚/追问消息。
- 限流保护：**每会话只发一次**、**每轮最多 N 条**（防平台风控）。
- 话术与阈值全部可用环境变量覆盖，可整体关闭。

## 7. 状态与配置项

**每店状态落盘**（按 店 × 账号 分文件）：场景卡冷却、已发商品卡、人工让位、已转人工、当前入口商品。

**环境变量（节选，全部可选）**

| 变量 | 作用 |
|---|---|
| `TAOBAO_SELLER_NICK` | 店铺主账号昵称（部分接口需要） |
| `TAOBAO_STAFF_NICK` | 当前客服账号昵称（**默认优先取账号名**） |
| `TAOBAO_TRANSFER_GROUP_ID` | 转人工客服组 ID（单店场景） |
| `TAOBAO_TRANSFER_ENABLED` | 是否启用转人工（`0` 关闭） |
| `TAOBAO_NUDGE` / `TAOBAO_NUDGE_TEXT` / `TAOBAO_NUDGE_AFTER_SEC` / `TAOBAO_NUDGE_MAX` | 主动触达：开关 / 话术 / 触发秒数 / 每轮上限 |
| `TAOBAO_CID_TIMEOUT_LIMIT` | 单会话连续拉取失败多少次后跳过 |
| `TAOBAO_MAX_CONCURRENT_LOAD` | 拉历史并发上限（`0` 关闭） |
| `TAOBAO_READ_TIMEOUT` | 读超时（慢会话场景可放宽） |
| `TAOBAO_DUMP_WS` / `TAOBAO_DUMP_FRAMES` | 抓帧诊断开关（排障用，默认关） |

**渠道分流**：账号管理器按渠道类型选择通道（同一进程内多渠道共存），通道自身不做平台判断。

## 8. 已知限制

1. **无"设置客服在线"的开放接口** —— 千牛在线态由客户端维持；通道侧的"上线"语义 = 接管并连上 WS。
2. **平台私有协议** —— 协议为逆向实现，平台改动可能导致通道短时失效，需要跟进维护。
3. **媒体跨店/跨机器不可直接共享** —— 平台媒体链接带时效签名（会过期），不能存死；跨渠道共享时**不带媒体**。
4. **带自定义结构的卡片**（非纯文本链接）目前只回通用话术、不查知识库——属已知盲点。
5. **登录态过期只能人工重新登录** —— 令牌刷新可自动完成，但登录态（会话）过期无法程序化恢复。
6. **同账号双端互踢** —— 平台机制：同一客服账号在多处登录会互相踢（表现为连接反复断开）。

## 9. 可选运维配套（部署方自行取舍）

- **健康探针**：定时检查各店连接状态、消息循环是否存活、近期回复失败/登录失败计数。
- **登录态保鲜**：定时刷新会话凭据（注意与平台令牌轮换配合）。
- **历史会话采集**：直调平台接口批量拉取历史会话，用于挖知识缺口（不依赖浏览器常驻）。
- **抓帧诊断**：环境变量打开 WS 帧转储，用于定位协议层问题（排障期短期开启）。

> 以上均为**外围可选脚本**，不属于通道本体；生产部署应配合自己的监控与告警策略。

5. `taobao_sender.py` —— 出站发送

7. `core/taobao_state.py` —— 会话状态
