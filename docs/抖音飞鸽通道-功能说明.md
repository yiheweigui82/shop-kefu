# 抖音 / 飞鸽（抖店）客服通道 · 功能说明

> 本文档描述一个**电商客服 agent 内核**里「抖音（抖店飞鸽）」渠道通道（Channel 插件）已实现的能力。
> 通道与同项目内的拼多多通道、淘宝 / 千牛通道**结构对称**：一个实例 = 一个店 = 一个独立线程 + 独立事件循环。
>
> 文档为**通用说明**：不含任何具体店铺、账号或部署环境信息。
>
> **通道形态一句话**：**收走协议层（站内 WebSocket），发走界面层（已登录的客服页面）** ——
> 前者让每店只吃一条连接、容量远高于「每店一个窗口」的方案；后者是绕开平台动态签名的工程取舍（见 §3）。

│   ├── douyin_connection.py 连接 + 指数退避重连
│   ├── douyin_source.py     飞鸽 WS 消息源（协议栈主体）

**与其它渠道共用**：消息队列 / 消费链 / AI 内核 / 双知识库 / 工具链完全复用 —— 通道只负责“接进来、发出去”。

## 2. 连接与协议（收）

| 能力 | 说明 |
|---|---|
| 站内 WS 长连 | `wss://ws.fxg.jinritemai.com/ws/v2` —— 抖店客服工作台的**站内**长连接（不是开放平台接口，也不需要开放平台权限） |
| 连接参数 | `token` / `websocketUrl` / `appId` / `fpId` / **`pigeon_sign`** 等来自工作台自己的取参接口，登录态（cookie）直调即可 |
| ★ 缺失即失败的参数 | **`access_key`**：取参接口**不返回**它，localStorage / sessionStorage / cookie 里也**都没有** —— 只在页面自己那条 WS 的 URL 里。缺它时服务端直接回 **HTTP 400**（现象与"签名错 / 参数名错"完全一样，极易误判）。取法：用 Playwright 打开工作台，**在页面导航前就挂 `page.on("websocket")` 监听**，等页面自己建连，从 URL 里取参落盘 |
| ⚠️ 参数编码 | `token` / `pigeon_sign` 是 base64 串（含 `+` `/`）→ **必须 URL 编码**；裸拼时 `+` 会被解析成空格，同样 400 |
| `device_id` | = **当前客服账号的 uid**（不是店铺号）；`device_platform=web` / `version_code` / `pigeon_source` / `PIGEON_BIZ_TYPE` 也要带齐（真实 URL 里都有） |
| 帧格式 | 外层 frontier 壳（`cmd` / `seq` / `serviceId` / `headers` / body），业务体是 **protobuf** —— **无官方 `.proto`**，字段号由实测反推（解析层用真实帧回归：283 条收帧正确解出 97 条消息） |
| 心跳 / 重连 | 指数退避重连；连接参数过期时重新取参重连 |

## 3. 发送（出）

**结论先说：这条通道的消息发送走「已登录的客服页面」，不走 HTTP 直调、也不走自建 WS 帧。** 三条路都实测过：

| 发送方式 | 实测结果 | 原因 |
|---|---|---|
| 自建 WS 帧 | ❌ **静默丢弃**（本地返回成功、客户收不到） | 页面那条 WS 只承载握手 / ack / 同步，不承载发消息 |
| HTTP 直调站内发送接口 | ❌ 业务码 `0` 但 **`reqId` 恒为空** = 服务端收下了请求、**没有创建消息** | 请求要带**页面 JS 现算**的风控令牌（`a_bogus` / `msToken` / `verifyFp`）——复制旧值无效、过期即静默失败 |
| **浏览器界面操作** | ✅ **真实送达（客户已读）** | 与平台自己的工作台同路 |

> ⭐ **判据提醒**：站内发送接口的 `reqId` **是发送成功的硬判据** —— 页面自己发时非空，空就是没发出去。
> **别拿业务码 `0` 当成功**，这是最容易误报「已发送」的地方。

**界面发送的工程实现**（`core/douyin_ui_sender.py`）：

- **专用线程**跑浏览器：Playwright 同步 API 要求同一线程内完成所有调用 → 自带线程 + 任务队列 + Future，对外暴露**同步** `send()`，异步侧再包一层线程调用。
- **必须先切会话**：界面发送只作用于「当前打开的那个会话」——这是这条路线的固有代价（HTTP 发送只认会话 id，界面发送认"当前会话"）。
- ✅ **发送前用输入框 `placeholder` 核对目标会话**（它是「发送给 <买家名>…」）——不符则**拒发**；`会话 id → 买家名` 映射缺失同样**拒发**（宁可报错，也绝不发错人）。
- **成功判据 = 输入框被清空**，不是「函数没抛异常」。
- 发送器按 **(店 × 账号) 单例**：每店一个常驻浏览器，避免反复弹窗与内存膨胀。
- 平台**没有「发送」按钮**（人工也是按 Enter 发送）→ 实现里就是填字 + Enter。
- 支持开关：默认只在明确要求时发送；探测模式不发送。

## 4. 消息接入与治理

| # | 问题（实测踩出来的） | 实现 |
|---|---|---|
| 1 | 店铺系统消息 / 客服自己的回复也被当客户问题再回一遍（回环、抢答） | 按消息属性里的**发送方业务角色**过滤：`Buyer` / `CurrentServer` / `Shop` —— **只有买家消息入队给 AI** |
| 2 | 控制包（状态变更类）混在消息流里 | 按 `msg_type` 丢弃控制包（它们不是客户发言） |
| 3 | ★ **平台会把同一条消息重复推送 2~4 次**（实测 35 帧 → 14 条唯一消息） | **幂等去重**：用客户端消息 id 作键 —— 服务端下发的 `server_id` 每次推送都不同，**拿它去重等于没去重**（客户会被回 2~4 遍） |
| 4 | 图片 / 视频与纯文本的 `msg_type` 相同 → 只看文案占位符会被平台改文案打穿 | **结构优先、文案兜底**：图片看属性里的图片直链 + 缩略图 + 宽高；视频看渲染模型 JSON（封面 / vid / 时长 / 宽高） |
| 5 | 媒体直链带时效签名 | 链接**带 `x-expires`（会过期）→ 不能存死**；跨渠道共享时不带媒体（与其它通道同口径） |
| 6 | 新会话发现 | 站内推送 + 会话列表兜底 |

**媒体能力**：

| 类型 | 接收（解析） | 说明 |
|---|---|---|
| 文本 | ✅ | 直接入对话上下文 |
| 图片 | ✅ | 直链（带签名）+ 缩略图 + 宽高；走视觉预处理注入上下文 |
| 视频 | ✅ | **只有封面 + `vid` + 时长，没有可直接播放的地址**（`vid` → 播放地址未打通） |

## 5. 登录模型（**半自动：第一次必须人工**）

实测：账密登录后会触发平台风控 → 需要**邮箱验证码**才能进。

- ⛔ **无人值守自动重登做不到**（验证码必须人工过）。
- ✅ 所以：登录走**有头浏览器**，程序**自动填账密**（省掉手输），滑块 / 验证码由人工完成；登录成功后当场完成三件事并落盘：
  1. 抓登录态（cookie）；
  2. **嗅探页面自己那条 WS 的连接参数**（含 `access_key`，见 §2）；
  3. 拉该店客服组列表 + 店铺信息（店名 / 店标 / 店铺 ID，见 §7）。
- ✅ 之后免重登：**登录态持久化**（独立浏览器 profile）+ 用 cookie 换会话 token（token 可刷新）。
- ⚠️ 登录态真失效 → 明确报「登录态过期，需人工重登」，**不当网络抖动反复重试**。
- **密码保留在本地**（加密存储）用于掉线后重登 —— 与其它通道一致。

## 6. 商品知识同步

「知识库」页一键同步即拉取本站商品 → 多模态 LLM 提取知识入库。

| 环节 | 做法 |
|---|---|
| 数据源 | 商品管理页（`fxg.jinritemai.com/ffa/g/list`）页面自身发出的商品列表接口 |
| ★ 不复制签名 | 该接口带**页面现算**的签名令牌（`a_bogus` / `msToken` / `verifyFp`）→ 通道**不复制、不复刻**：打开商品页、**只听页面自己的响应**；翻页靠**点页面上的页码**（让页面自己重发请求） |
| ⚠️ 前置空查询 | 页面首次会连发多个列表请求，**前面几个是空的**（`total=0`）→ 必须**按页归档、取条目最全的那份**，否则「一有响应就用」必然拿到空集 |
| **分页契约** ⚠️ | 同步服务是「按页循环、**某页返回空才停**」→ 实现里必须**内部只拉一次全量 + 缓存，再按 (page, size) 本地切片**；若忽略分页参数、每次都返回全量 → **永远返回不满 → 死循环** |
| **详情兜底** ⚠️ | 详情取不到会让整个店「同步成功 0 个」（静默全失败）→ 实现用**列表已有字段兜底**（名称 / 价格 / 库存 / 销量 / 类目 / 主图 / 链接），规格参数留空数组，**不假造** |
| 价格单位 | 平台返回**分** → 展示前除以 100 |
| 字段映射 | 商品 id / 名称 / 主图 / 价格 / 原价 / 库存 / 销量 / 类目 / 商品链接 |
| 增量 vs 全量 | **增量**（默认）：跳过本地已存在的商品（不重提知识、不动旧数据）—— 适合先验链路；**全量**：重抓全部并覆盖已提取知识 —— 适合统一刷新 |
| 浏览器 | 有头（平台风控较严，有头更稳），每个同步实例复用一个浏览器，**同步结束即关闭**；探测/同步不占用常驻发送器的 profile |

**实测**：某店一轮同步 `26 个商品 / 成功 26 / 失败 0`，约 3 分 20 秒；每条提取知识约 500~1100 字，全部带主图。

## 7. 新店接入的自动化

**加一个账号 = 只填两栏（账号 + 密码），其余全自动。** 登录成功后：

**① 店铺信息一次拉全** —— 工作台自己的接口一次返回：**店铺名 · 平台真实店铺 ID · 店标**（+ 账号 uid）。
> ⚠️ 别从页面 DOM 里捞：工作台顶部那个小圆图是**客服头像**，它的替代文本是**客服昵称**，既不是店名也不是店标。
> 店号直接用**平台真实店铺 ID**（不再自编号），所以加店时**不用填店号**；店已存在时用本次抓到的值**更新**店名/店标（抓不到绝不清空）。

**② 客服组列表** —— 登录当场拉该店全部客服组并缓存（转人工时按组名实时匹配，见 §8）。

**③ WS 连接参数** —— 含 `access_key`（见 §2），落盘后直连复用，不必反复登录。

## 8. 转人工

飞鸽**只支持「转给客服组」**（没有转单个客服的接口），而且**后台不显示明文组 ID** → 组 ID 只能自己取。全链路**纯 HTTP，三步**：

```
① GET  取店铺客服组列表（只读，无请求体）
       → [{groupId, groupName, onlineStatus, customerCount, ...}]
② POST transfer/pre_check      {"securityUserId": "<买家加密 uid>"}   # 每个候选组一次
③ POST conversationToShopGroup {"groupId":…, "fromStaffId":…, "receiverUid":…, "ignoreSnap":false, ...}
```

| 设计 | 说明 |
|---|---|
| **配置只写组名关键词** | 配置里写「售后 / 售前」这类**组名关键词**，不写数字 id —— 转人工时**实时查表取 id**，组 id 变了 / 新增组都**不用改配置** |
| **按诉求排候选 + 失败自动回退** | 按组名匹配出候选顺序（命中关键词 → 有人在线 → 待接少 → 名字更"专属"），**逐个试**；某组**当前无人值班**（平台回「该分组找不到可以转交的客服」）→ **自动换下一组** |
| 中止回退 | 只有两种：① 平台说「转交对象就是当前接待账号」（转给自己，换组无意义）；② 该店未配置任何组 |
| 话术注意 | 转人工**没被接起**时，**平台自己会回**「亲，目前人工坐席正忙…」—— 自配话术要避开重复 |
| 不做假承诺 | 平台做不到的类型（如"转指定客服"）→ **明确返回不支持**，绝不假成功 |

## 9. 已知限制

1. **发送依赖界面层** —— 发送走「一个已登录的客服页面」：必须先切到目标会话、秒级延迟；平台页面改版可能导致失效。这是为绕开**页面现算的动态签名**付出的代价（协议层发送暂不可行）。
2. **媒体发送未上线** —— 图片的发送结构已探明（与发文字同接口，换消息类型并带素材库图片 uri，**发素材库已有的图可行**），但**任意本地图的上传接口未打通**；视频的发送结构尚未抓到 → `send_image` / `send_video` **保持如实声明为不支持**，不做假成功。
3. **登录态只能半自动恢复** —— 验证码必须人工过，掉线重登做不到无人值守。
4. **平台私有协议** —— 站内 WS 与帧字段号均为实测反推，平台改动可能导致通道短时失效。
5. **媒体链接带时效签名** —— 会过期，不能存死；视频只有 `vid`、无可播地址。
6. **同店禁止双开** —— 同一抖店在两台机器 / 两个进程同时在线 = 消息双发，平台也可能互踢（红线）。
7. **无「设置客服在线」的开放接口** —— 通道侧的「上线」= 接管并连上长连接。
