# 电商客服 Agent · 功能说明（多平台渠道）

> 本文档描述一个**桌面端电商客服 agent**（PyQt 图形界面 + 多平台渠道 + AI 自动回复）已实现的功能。
> **一个进程可同时接入多个平台、多个店铺**：一个店 = 一个独立线程 + 独立事件循环，互不阻塞。
> 文档为**通用版**：不含任何具体店铺、账号或部署环境信息。

## 1. 总体架构

```
                 ┌──────────────── 图形界面（桌面端）────────────────┐
                 │ 自动回复 / 账号管理 / 知识库 / 关键词 / 日志 / 设置 │
                 └──────────────────────┬───────────────────────────┘
                                        │
        ┌───────────────┬───────────────┴───────────────┬───────────────┐
        │  渠道：拼多多  │        渠道：淘宝 / 千牛        │  （可扩展）    │
        │  Channel/pdd   │        Channel/taobao          │  Channel/…     │
        └───────┬───────┴───────────────┬────────────────┴───────┬───────┘
                │   统一上下文 / 发送器（bridge）│                 │
                └───────────────┬───────────────┘                 │
                        ┌───────▼────────┐                        │
                        │  消息队列 + 消费链 │◄───────────────────────┘
                        │ 预处理→关键词→AI  │
                        └───────┬────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │ AI 内核：多轮工具调用 + 知识库检索 │
                 └─────────────────────────────┘
```

要点：

- **渠道插件化**：新增平台 = 新增一个 Channel 插件，AI 内核与消息链路不改动。
- **统一发送抽象**：`bridge.sender` 定义 `send_text / send_image / send_video / send_product_card`，按渠道分发。
- **统一消息链路**：所有渠道的消息都进同一套「队列 → 消费器 → 处理器链（预处理 → 关键词 → AI）」。
- **每会话一条队列**：同一客户的消息串行处理，不同店铺互不阻塞。

## 2. 渠道 A：拼多多

| 能力 | 说明 |
|---|---|
| 实时消息 | WebSocket 长连接接收买家消息；多店多线程 |
| 断线自愈 | 指数退避自动重连（有限次）；**修复了「连接断开但进程活着不触发重连」的经典坑**（连接异常结束时主动抛错进入重试分支） |
| 心跳保活 | 定时心跳；心跳异常计入失败计数 |
| 凭据健康检查 | 检测登录态失效 → 自动刷新/重登，成功后写回本地库 |
| 启动接管 | 启动时自动接管所有「在线」账号（无人值守）；可整体关闭 |
| 场景卡 | 处理「商品规格卡」与「用户来源卡」两类结构化卡片，拿到客户咨询的商品上下文（客户从商品页进客服时，AI 能知道他在看哪款） |
| 发送能力 | 文本 / 图片 / 视频 / 商品卡 |
| 平台限流 | 「买家回复前不能继续发送」等平台风控返回 → **不重试，改发文字**（避免被加重限制） |
| 转人工 | 拉取可分配客服列表 → 指定客服转接 |

## 3. 渠道 B：淘宝 / 千牛

| 能力 | 说明 |
|---|---|
| 协议栈 | 千牛 WS：换 accessToken（令牌过期自动刷新重试）→ 注册 → 同步流建立 → 定时心跳 → 逐帧 ack → 推送解密发现会话 → 拉历史消息 |
| 请求签名 | 本地 JS 引擎执行签名脚本（依赖 Node） |
| 令牌轮换 | 平台约 1.5 小时轮换签名令牌 → **收到响应即更新**，且主令牌与加密令牌**成对更新**（只更新一个会「非法令牌」） |
| 断线自愈 | 指数退避重连 + **读超时强制重连**（长连接僵死兜底） |
| 发送能力 | 文本 / 图片 / 视频 / 商品卡 |
| 场景卡主动接话 | 客户从商品详情页 / 订单页入口进来 → **主动问好**（不沉默等待）；按卡片类型**分别冷却** |
| 转回后问好 | 平台把会话转回来 → 主动问好（冷却键独立） |
| 回复后补商品卡 | AI 回复后补一张相关商品卡；**只发 1 张、同款只发一次**（平台会拦截连续发卡） |
| 人工让位 | 人工客服刚说过话，或会话已转人工 → **AI 不插话** |
| 漏回主动触达 | 客户发言超阈值（默认 30 分钟）而无人回复 → 主动发一条；每会话一次、每轮限条数（防风控） |
| 转人工 | 走平台 mtop 接口，目标为**客服分流组 ID**（见 §7） |
| ⚠️ 无在线态接口 | 平台未开放「设置客服在线」接口，在线态由客户端维持；通道侧「上线」= 接管并连上 WS |

## 4. ⭐ 媒体发送（图片 / 视频）

两个渠道**都支持发图片和视频**，由 AI 在对话中按需自动发送（也可由关键词/规则触发）。

### 4.1 统一调用链（AI 侧零改动）

```
AI 决定发媒体
  → 工具 send_media(media_type=image|video, media_url=…)
  → bridge.sender.get_sender(渠道)      ← 按渠道分发
  → 渠道自己的 send_image / send_video
  → 平台协议发送
```

- 工具参数：`media_type`（`image` / `video`）、`media_url`、以及会话身份（店铺/账号/接收人）。
- **AI 侧不用关心平台差异**——渠道适配层吸收全部协议细节。

### 4.2 两平台协议差异（核心表）

| | 拼多多 | 淘宝 / 千牛 |
|---|---|---|
| 图片 | 消息 `type=1`，直接给图片 URL | 走消息接口的图片消息结构（见下） |
| 视频 | 消息 `type=2`，直接给视频 URL | **`contentType=101` + `custom.data`**（结构化，见 §4.3） |
| 媒体 CDN | 直链长期有效 | CDN 链接**带时效签名**（约 17 小时过期） |
| 长期地址 | 直链即长期 | **有**：由素材 ID 拼出的公开播放地址（无签名，长期有效） |
| 封面 | 平台图床 | 平台图床（素材条目里带封面地址） |
| 商品卡 | 商品卡片消息 | 文本消息内嵌模板参数（**连发第 2 张会被平台拦截**） |

> 结论：淘宝侧**优先使用长期播放地址**（免过期），时效签名链接仅作兜底；拼多多侧直链直接可用。

### 4.3 淘宝视频消息结构（实拍 + 抓包双向验证）

与文本走**同一个**发送接口，只是换 `content`：

```json
{
  "content": {
    "contentType": 101,
    "custom": {
      "summary": "", "title": "", "type": 9, "degrade": "",
      "data": "<base64 of {duration,width,height,pic,mediaId,url,size}>"
    }
  }
}
```

- `data` 是**结构化字段的 base64**（时长/宽高/封面/素材 ID/播放地址/体积）。
- 缺 `mediaId` / 封面时，发送端会**自动反查素材库补齐**，调用方只给 URL 也能发。
- 同接口的其它形态：文本 `contentType=1` + 文本内容；商品卡 `contentType=1` + 模板参数；系统/场景卡 `contentType=101` + 卡片类型。

### 4.4 素材存储：按平台分版

知识条目带一个媒体列（JSON），**按平台分桶**：

```json
{
  "taobao":     [{"kind":"video","media_id":"…","cover":"…","url":"<长期播放地址>",
                  "auth_url":"<带签名地址>","duration":15,"width":720,"height":1080,"size":…,"title":"…"}],
  "pinduoduo":  [{"kind":"video","url":"<直链>"}]
}
```

- 检索时**只吐本店所在平台**的媒体；**跨店/跨机器共享知识时不带媒体**（因为媒体链接往往与账号/时效绑定）。
- 数据库加媒体列**必须同步 ORM 字段**，否则取值静默为空。

### 4.5 什么时候会发媒体（触发规则）

- 客户问**操作类问题**（怎么安装 / 怎么调 / 怎么用 / 怎么选型 / 有没有教程 / 有视频吗…）→
  **只要该商品存在视频素材，就必须先把视频发出去，再补文字说明**；
  提示词里显式强调「**即使你能用文字答上来，也必须先发视频**」（否则模型会走省事路径只回文字）。
- 客户索要图片/安装示意 → 同样优先真实发送，**不允许"说发您"却未发**（假承诺）。
- 没有对应素材 → 正常文字回答；答不了再转人工。

### 4.6 失败与风控

| 平台返回 | 含义 | 处置 |
|---|---|---|
| 陌生消息拦截 | 平台限制对该买家发消息 | 记日志、不重试 |
| 连发商品卡被拦截 | 短时间重复发卡 | 设计为**只发一张、同款只发一次** |
| 买家回复前限制发送 | 平台限流 | **不重试**，改发文字回复 |

## 5. AI 内核与工具链

- **多轮工具调用**：模型可连续调用工具（查商品知识 → 查政策 → 发商品卡 → 发媒体 → 转人工）。
- **工具集**：商品知识查询、商品列表、客服知识检索、发商品卡、**发图片/视频**、转人工、查补货/补发等（按渠道与业务扩展）。
- **会话上下文**：对话历史落库，支持多轮上下文与跨轮澄清。
- **视觉理解**：客户发的图片/视频先过视觉预处理，识别结果注入上下文（识别破损、规格、颜色、订单信息等）。
- **行为护栏**（提示词 + 出口自检双保险）：
  - **转人工话术前置**：必须先真的调用转人工工具且成功，才允许对客户说"已转人工"；未成功则如实说明。
  - **不让假承诺**：说"发您视频/教程"必须真发出；没发不许说。
  - **转人工后拦在途回复**：会话已转人工后，模型处理到一半的回复会被**拦截**（避免"转了人工还插话"）。
  - **兜底不骗人**：生成失败时先尝试真转人工，再按结果如实答复。
  - **经营口径统一**：补偿/质保/赠品/议价等敏感话术由统一口径约束，且**不主动亮补偿上限**。

## 6. 知识库

| 库 | 粒度 | 用途 |
|---|---|---|
| **商品知识** | 每个商品一条 | 规格/材质/尺寸/价格区间/卖点/常见问答/(可选)媒体 |
| **客服知识** | 每个主题一条、全店共用 | 售后、物流、退换货、质保、活动规则、FAQ |

- **自动同步**：从平台拉商品列表 → 多模态模型提取 → 入库（含从图片提取的卖点）。
- **跨店 / 跨平台复用**：同款商品在一个店维护过，其它店/平台命中时**自动复用**（并**剔除来源店价格**等服务性字段，避免串价）。
- **即时生效**：知识改动实时生效，无需重启。
- **优先级**：店级/渠道级专属口径 > 通用话术（可按店注入覆盖段）。

## 7. 转人工

| | 拼多多 | 淘宝 / 千牛 |
|---|---|---|
| 机制 | 拉取可分配客服列表 → 指定客服转接 | 平台接口 → **客服分流组**（组自动探测并落盘，含组名） |
| 关键配置 | 客服列表接口权限 | 客服组**登录时自动探测**；配置文件映射 / 环境变量只作兜底 |
| 分派策略 | — | **按诉求分派 + 失败自动回退**：客服组按组名分「售前 / 售后」，按客户诉求先试匹配的那组；该组当前无人值班（平台返回「分组里找不到客服」）→ **自动换另一组**（只有"转给自己"或"本店未配组"才中止） |
| 常见返回 | 人工不在线（夜间） | 分组里找不到客服（组无人 / 组配错）/ 转交失败（未配组）/ 令牌过期（可自动刷新）/ 会话过期（需重新登录） |

通用能力：

- **夜间/无人工时段**：如实告知客户，并（可选）**次日自动补转**深夜未转成的会话。
- **独立直连脚本**：不依赖常驻进程，可直连平台接口发起转接（用于批量补转/排障）。
- **转接成功可核实**：记录"该会话真的转成功过"的标记，供出口自检判断可否说"已转人工"。
- **诉求判据 = 确定性代码**（淘宝/千牛侧）：会话里出现**订单信号**（消息扩展字段的订单号、订单入口场景卡）
  或客户话里明说**售后问题**（退/换/修/破损/漏发/质量…）→ 售后；否则 → 售前。
  逐条可单测，不依赖模型判断；判错也有回退兜底。

## 8. 消息治理与可靠性

**拼多多侧**

- 断线自愈（指数退避）+ 心跳 + 凭据健康检查。
- 「假在线」防护：平台侧可能静默重置客服状态而连接不断 → 由**外部健康巡检**发现（见 §9）。

**淘宝侧**（生产实测问题 → 实现）

| 问题 | 实现 |
|---|---|
| 会话 id 多写法导致判重失效 | 会话 id **归一化**（保留买家段），判重/在途/失败计数统一 |
| 进程重启后老消息被**重放**（同一客户被连回多次） | 已处理消息指纹落盘；**投递新消息立即落盘**（不等批量） |
| 个别会话永远拉不到 → 拖慢整轮 | 失败达阈值加入"僵尸会话"跳过；**收到推送自动救回** |
| 长时间无新消息的会话空转烧接口 | **空转降频**（实测接口调用省约 **87%**）；来新消息立刻恢复 |
| 串行拉取被单个慢会话堵住 | 改**并发** + **并发上限** + 防重入 |
| 客户连发多条 → 逐条回复刷屏 | **消息合并器**：窗口内合并为一段；含媒体时整窗只发一条安抚 |
| 平台本地接待列表文件停更 → 漏收消息 | 接待列表**双源**（本地文件 + 远程接口） |

**双渠道共性**

- **每会话一条队列**，同客户消息串行；跨会话/跨店并行。
- **发送去重/冷却**：同一商品卡只发一次、转人工冷却、场景话术分类冷却。

## 9. 运行、状态与配置

**运行形态**

- 桌面应用（图形界面）：账号管理、自动回复卡片、知识库、关键词、日志、设置。
- 启动即**无人值守接管**「在线」账号；可一键停止某店或整体下线（改账号状态 + 重启）。
- 营业时段可配置（默认 08:00–23:00）。

**状态落盘**

- 每店每账号一份会话状态：场景卡冷却、已发商品卡、人工让位、已转人工、当前入口商品。

**配置项（节选，均可选）**

| 变量 | 作用 |
|---|---|
| 媒体/视频库 | 视频库素材清单（标题 + 地址 + 标签） |
| `*_NUDGE*` | 漏回主动触达：开关 / 话术 / 触发秒数 / 每轮上限 |
| `*_SELLER_NICK` / `*_STAFF_NICK` | 店铺主账号 / 当前客服账号昵称 |
| `*_TRANSFER_GROUP_ID` / `*_TRANSFER_ENABLED` | 转人工客服组 / 开关 |
| `*_CID_TIMEOUT_LIMIT` | 单会话连续拉取失败阈值（跳过僵尸会话） |
| `*_MAX_CONCURRENT_LOAD` | 拉历史并发上限 |
| `*_READ_TIMEOUT` | 读超时（慢会话场景放宽） |
| `*_DUMP_WS` / `*_DUMP_FRAMES` | 抓帧诊断开关（排障用，默认关） |
| `CUSTOMER_AGENT_AUTO_REPLY=0` | 不自动接待（下线模式） |

**外部健康巡检（可选配套）**

- 定时检查：进程存活 / 各店连接状态 / 消息循环是否异常结束未恢复 / 近期回复失败与登录失败计数。
- 语义：**只在异常时输出**（正常即静默），异常推送给人处理。
- ⚠️ 排查「回复发送失败」时先识别**设计内拦截**（转人工后拦下在途回复会被记成发送失败）——这属误报来源。

## 10. 已知限制

1. **平台私有协议**：两个渠道的协议均为逆向实现，平台改动可能导致短时失效，需要跟进维护。
2. **无在线态接口（淘宝）**：在线状态由客户端维持，程序侧只能"接管/断开"。
3. **登录态过期必须人工重登**：令牌可自动刷新，但会话过期只能人工（扫码/验证码）重新登录。
4. **同账号双端互踢**：同一客服账号在多处登录会互相踢（连接反复断开/直接掉线）——这是平台机制，不是程序缺陷。
5. **媒体不可跨平台/跨机器直接共享**：媒体链接常带账号或时效绑定，跨渠道共享知识时**不带媒体**。
6. **带自定义结构的卡片**（非纯文本链接）目前只回通用话术、不查知识库——已知盲点。
7. **"假在线"需外部巡检发现**：平台静默重置客服状态时连接与凭据都正常，程序自身难以感知。
8. **夜间无人工时段**：转人工会被平台拒绝，需要"次日补转"或人工回访机制配合。
